# A Product Brain OS
### Concept design — problem space first, then the system
*Working draft v0.1 · July 2026*

---

## 1 · Why "Cursor for PMs" is the wrong first question

Cursor works not because a model writes code, but because the model operates inside a world that is already machine-legible. The repository is a complete, centralized, versioned representation of the work. Git provides history and reversibility. The type system and test suite provide cheap verification. The agent can read the true state of the work, act on it, check its own output, and every mistake is revertible. Cursor didn't have to build any of that — it inherited fifty years of substrate and put an agent on top.

Product work has no such substrate. The PM's "codebase" is smeared across Jira, Notion, Slack, Gong, Amplitude, Figma, email — and, critically, across people's heads and hallway conversations. There is no compiler for a PRD, no test suite for a roadmap, no git log for "why did we descope SSO." So the honest formulation of this product is: **before anyone can build Cursor for PMs, someone has to build the repo for PMs.** That repo is the product brain. The agent is the second thing you build. The tools currently bolting AI drafting onto doc editors are building Cursor without git — which is why they produce plausible text and no compounding value.

The one-sentence thesis: *a versioned, evidence-linked model of what the product team believes, has decided, and has promised — with an agent that operates on it, and a shell that never shows a command line.*

## 2 · The problem space

### 2.1 What the work actually is

The Value Chain framing — **Signals → Insights → Artifacts → Alignment** — is the right anatomy. Signals arrive continuously (calls, tickets, threads, metrics, competitor moves, exec opinions). Insights are the judgments formed from them. Artifacts are the durable renderings (PRDs, roadmaps, one-pagers, updates). Alignment is the ongoing work of projecting the same truth into many heads.

Two things about this chain matter for design. First, the highest-pain work lives in the *seams*: turning forty signals into three insights, keeping an artifact honest as reality moves, re-explaining the same state to the fifth stakeholder this week. Every incumbent tool serves a station; nothing serves the line. Second, the chain is a loop, not a pipe — alignment produces new signals (exec pushback, an engineering constraint surfaced in review), and a PM's day is interrupt-driven by it: "what's the status of X, and why?" asked over and over, each answer assembled by hand from four tabs and memory.

### 2.2 Five structural differences from coding

These are the reasons the Cursor analogy breaks if applied naively, and each one is a design constraint in disguise.

**There is no shared substrate.** Described above; it is the founding problem. Consequence: the substrate must be built — and built as a *derived* layer that assembles itself out of the tools already in use. Any design that requires data entry or migration is dead on arrival.

**Verification is the expensive half.** In code, generation was historically costly and verification comparatively cheap — compile it, run the tests. AI made generation nearly free, which moved the bottleneck to verification. In product work, verification was *already* the dominant cost: checking a confident, plausible-but-unsourced claim in a draft PRD costs more than writing the sentence yourself. This is the verification tax that keeps showing up in practitioner interviews, and it means a naive drafting tool makes a good PM net slower. Consequence: **the unit of trust must be the sentence, not the document.** Every generated statement either carries a link to its evidence or is visibly marked as the machine's inference. This cannot be a prompt aspiration; it has to be enforced by architecture (§4).

**Decisions are unversioned.** Code has commits and blame. Product direction has vibes and stale docs. The most valuable question in product work — *why is it like this?* — is answered today by Slack archaeology and tribal memory, and it is asked constantly: by new engineers, by execs relitigating last quarter, by the PM's own future self. Consequence: decisions become first-class, versioned objects with rationale and supersession — a git log for direction. (This is also the gap in the Value Chain model: decisions sit between Insights and Artifacts. The model implies them but doesn't name them; the object model below does.)

**The org is the runtime.** A developer ships to a machine; a PM ships to an organization. Most "writing" a PM does is re-rendering the same underlying state for different audiences — exec brief, eng detail, sales talking points, the Friday update. Consequence: a status update is not a document, it is a *render*: a query over current state, projected for an audience. If state is structured, updates become views, and their marginal cost approaches zero.

**Actions are socially irreversible.** Cursor can auto-apply a diff because git makes everything reversible. A message to your CPO has no revert. PM artifacts are also political instruments; an agent that speaks to the organization uninvited is an adoption killer, not a feature. Consequence: autonomy must be graduated by blast radius — free inside the brain, where everything is reversible by design; propose-only across the boundary to humans.

### 2.3 The four practitioner pains, restated as constraints

**Tool sprawl** → be a *layer*, not a tool. Replace nothing on day one; sit between the existing tools; deliver outputs into the places stakeholders already live. The pitch must never be "one more tab that owns your data" — it is "the layer that ends the swivel-chair work between the tabs."

**Missing workflow context** → context is the product. The agent's working context must be persistent, inspectable, and correctable. The user can always see exactly what the machine is looking at, and change it.

**Verification tax** → provenance at sentence granularity, review as tracked changes, never a wall of unsourced prose.

**Role-identity anxiety** → the posture is chief of staff, not auto-PM. It prepares; the PM decides. And it should make the PM *more* formidable in the room — every recommendation backed by clickable receipts — rather than more replaceable. A tool that visibly amplifies judgment gets adopted; a tool that impersonates judgment gets sabotaged.

### 2.4 Cold-start economics

Cursor's cold start is zero: open the repo. This product's cold start is its hardest problem, because the brain is only valuable once populated. Constraint: the brain must populate (a) automatically, by backfilling connectors, and (b) as a *byproduct* of work the PM would do anyway — drafting an update ingests what changed; answering a question caches the answer as knowledge. Value must exceed effort within the first session, single-player, with no team buy-in required.

### 2.5 The design constraints, collected

1. The substrate is derived and assembles itself; no data-entry chore, no migration.
2. Every generated sentence is cited to evidence or labeled as inference.
3. All writes are suggestions until trust is earned, workflow by workflow.
4. Autonomy scales with reversibility; nothing leaves the workspace unapproved.
5. Replace no tools on day one.
6. Single-player value inside the first session.
7. No command syntax anywhere — selection, contextual verbs, @-mentions, plain language; every automation readable as an English sentence.
8. The PM is editor-in-chief: the product prepares, the human decides.

Everything below is derived from these eight.

## 3 · The concept model

Six objects. Deliberately few — ontology sprawl is how PM tools die. Structure beyond these six should be emergent (tags, saved queries), never new primitives.

**Source.** An immutable ingested record: a call transcript, a ticket, a Slack thread, a doc revision, a metric snapshot, an email. Carries origin, timestamp, participants. Never edited, only referenced. *(Value Chain: Signals.)*

**Claim.** The atom of the brain: one checkable statement in plain language. "Q2 enterprise churn interviews repeatedly cite onboarding time." "The auth vendor has committed SCIM support by November." A claim has: the statement; evidence links pointing to source *spans* (the ninety seconds of the call, not the whole call); a type — *fact* (state of the world), *insight* (interpretation), or *commitment* (someone said they'd do something); a confidence level; a status (proposed → confirmed → disputed → superseded); and a freshness policy with a last-verified date. Claims may conflict, and conflicts are surfaced, never silently resolved — a conflict between claims is precisely the kind of thing that requires a human. Claims are extracted by the agent and confirmed by the PM, either explicitly in review or implicitly by using them in an artifact. *(Value Chain: Insights, plus the plainer facts underneath them.)*

**Decision.** The spine of the brain and its most novel object: the chosen option, the alternatives considered, the rationale as links to claims, the decider, the date, and a status — *active* or *superseded-by*. Every "why" question terminates at a decision. Reversing course means superseding with reasons, never editing history. Six months from now, "why did we descope SSO?" is a two-second lookup with the original evidence attached, instead of an afternoon of archaeology.

**Artifact.** A human-readable document: PRD, one-pager, roadmap entry, weekly update. Composed of static prose plus **live sections** bound to claims or saved queries. Live sections carry **health** — are the underlying claims still fresh? — and they never mutate silently: when reality moves, the artifact grows a *suggestion*, not an edit. A document you presented yesterday must never read differently today without your explicit accept. Artifacts render into **views** per audience — exec, eng, sales — derived on demand and watermarked "as of." *(Value Chain: Artifacts, with views doing the work of Alignment.)*

**Playbook.** A saved workflow, defined and displayed as plain English in a fixed grammar: **When / Read / Produce / Then.**

> **When** every Friday at 15:00 · **Read** changes in Jira project ATLAS, #launch-x, and this week's call transcripts · **Produce** a draft of the *Weekly Update* artifact · **Then** hold it for my approval.

Each slot is a structured chip rendered as prose — legible like a sentence, precise like a form. Playbooks have a run history, an accept rate, and a trust setting (§6). This is the no-code equivalent of an agent skill, and it is how the product grows: a new capability is a new playbook, which is content, not a feature release.

**Suggestion.** The universal write primitive. The agent can never mutate anything directly; every proposed change — a new claim, an artifact edit, a drafted decision, an outbound message — is a Suggestion carrying a *diff* (rendered as tracked changes), a *because* (one-line rationale), and *receipts* (evidence links). Reviewing a suggestion is the tracked-changes gesture every PM already knows from Google Docs. Accepting one is a single tap — and also a trust signal that accrues to the playbook that produced it.

The relationships in one breath: **Sources ground Claims; Claims justify Decisions; Claims and Decisions compose Artifacts; Artifacts render as Views for audiences; Playbooks read everything and write only Suggestions; Suggestions are the only way anything changes.**

**Freshness is a first-class property.** Facts decay at different rates: metric claims in days, commitments at their due dates, strategy claims in quarters. Each claim type has a decay policy; a nightly playbook re-verifies decaying claims against their sources and files suggestions where reality has moved. An artifact's health score — the share of its live claims that are fresh — is the closest thing product work will ever have to a failing test. Not "is this true," which no machine can promise, but "is this still supported by current evidence," which it can.

**The provenance rule.** The product-level guarantee, worth printing on the landing page: *every sentence the agent asserts is either cited to a source span or explicitly styled as its own inference.* Not a hope about model behavior — a property of the write path, enforced where the agent touches the world (§4).

## 4 · Architecture: brain, harness, shell

Three layers, deliberately pi-shaped.

**Why the pi pattern.** pi (pi.dev) is a minimal agent harness: a tiny agent loop around a four-tool core with a sub-thousand-token system prompt, where everything else — tools, context management, skills, memory, even permissions — is a typed extension, and the whole thing runs interactive, headless, or embedded in another app via RPC/SDK. Two of its properties matter enormously here. First, the harness is an implementation detail: the terminal UI is just one shell, and the same loop can sit invisibly inside a friendly application. Second, pi deliberately ships *no* permission system — boundaries are the builder's job. For this product that is exactly right, because **the trust layer is the product.** The lesson underneath both: the model is rented; the harness plus the substrate is what you own.

**Layer 1 — the Brain (substrate).** Connectors — Jira/Linear, Slack, the call recorder, Notion/Confluence, analytics, email/calendar — sync **read-only by default** into an object store, a graph over the six objects, and a retrieval index. Everything in the brain is derived and rebuildable: a trust failure is recoverable, and procurement risk stays low, because read-only scopes are what a security review wants to see (this buyer is familiar territory from fintech; lead with the scopes one-pager). The brain, not the model, is the moat — every confirmed claim and every logged decision raises switching cost, and none of it ships with a competitor's Jira import.

**Layer 2 — the Harness (pi-shaped core).** A small agent loop whose *only* access to the world is a set of typed tools: `brain.search`, `brain.evidence(claim)`, `brain.propose(suggestion)`, `connector.query`, `artifact.diff`, `outbound.draft`, and so on. The provenance rule lives in the tool contract: `propose()` rejects any asserted sentence that lacks evidence handles unless it is flagged as inference, and the shell styles inference differently. The guarantee is therefore architectural — the agent *cannot* state what it cannot cite, regardless of what the model would like to say. Skills are playbooks: packaged instructions plus tool sequences, loaded on demand. Extensions are connectors and shell hooks. Sessions are stored, replayable transcripts of every run — when trust breaks ("why did it claim X?"), you open the session and watch exactly which sources led where; an audit trail by construction, which regulated buyers will also love. Long-horizon jobs run headless: the overnight shift that re-verifies decaying claims and preps Friday's drafts before the PM wakes up. The provider layer is model-agnostic, so every model generation lifts the whole product with zero rework. Build option: literally embed pi through its SDK/RPC mode, or adopt the pattern with a thin loop of your own — either way the discipline is identical: small core, capabilities as content.

**Layer 3 — the Shell.** The application PMs actually see (§5). The harness never surfaces. No terminal, no slash grammar, no "agent is calling tool `brain.search`" narration. The only place the machinery shows is the receipts.

The compounding trick of this shape: because capabilities are playbooks and playbooks are content, a two-person team can ship "features" weekly without touching the core — and every improvement to the core (retrieval, extraction, the loop) improves every playbook at once.

## 5 · The interface, without a command line

For developers, the command line is precision. For PMs, **selection is the command line, and English is the scripting language.** Seven concepts carry the whole shell.

**The Desk.** One layout everywhere: the thing being worked on in the center — an artifact, the claim browser, a review — and the agent panel beside it, always contextual to what's open and selected. Cursor's geometry, with PM materials where the code would be.

**Context chips.** Pinned at the top of the agent panel: what the agent is currently looking at, as removable, addable chips — *PRD: Onboarding v2 · last 5 sales calls · Jira: ATLAS*. Adding context is an @-mention, a gesture PMs already know from Slack and Notion (keep @, kill /). Two pains die at once: "the AI doesn't know my context" and its evil twin, "I can't tell what it knows."

**Selection as scope.** Highlight anything — a paragraph, a claim, a row — and contextual verbs appear as chips: *Verify · Expand with evidence · Rewrite for [audience] · Turn into ticket · Ask about this.* Verbs adapt to what's selected; a free-text box sits beside them for everything else. Nothing to memorize, ever.

**Tracked-changes review.** Every agent write arrives as a Suggestion rendered in tracked changes with its *because* and its *receipts*. Granular accept and reject; batch-accept for the trivial. One familiar gesture simultaneously solves verification, trust, and control — this is the PR review, translated into the one diff format every PM already reads fluently.

**The Inbox.** Home is not a dashboard; it is a queue of judgment calls: suggestions to review, conflicts between claims, questions the agent couldn't answer, decisions awaiting a decider, staleness alerts — ranked, with a reachable zero. A dashboard says "look how much is happening." An inbox says "here is what needs *you*." That difference is the answer to role-identity anxiety, embodied in the home screen.

**Ask, with receipts.** A global ask bar over the brain. Answers arrive as prose in which every sentence is hoverable to its evidence — "show me why" is always one click. Every answer offers two follow-ups: *Save as claim* (the answer becomes durable brain state) and *Send as view* (rendered for a chosen audience, held for approval). The loop this closes is the flywheel: answering questions builds the brain, and the brain answers questions.

**Playbook cards.** A gallery of prebuilt playbooks — weekly update, interview synthesis, launch checklist, decision logger, competitor watch. Opening a card shows its When/Read/Produce/Then sentence; editing it is editing the chips in the sentence. Before enabling anything: **dry run on last week** — "here is what this playbook would have produced last Friday, from your actual data." Nothing builds trust faster than a counterfactual with receipts.

**First run.** Connect three sources — tracker, Slack, call recorder. Ten minutes later, the **First Brief**: "here is what your product brain believes so far" — top themes, detected commitments, apparent open decisions, each with receipts and confirm / fix / discard controls. The confirm loop is onboarding, calibration, and the magic moment in one. The target reaction, inside session one, single-player: *it already knows my product.*

## 6 · Autonomy and trust

One rule generates the whole model: **autonomy scales with reversibility.**

- **Always autonomous:** read, index, link, flag staleness, prepare drafts in the background. Invisible, reversible, no state mutated.
- **Suggest — the default for every write:** new claims, artifact edits, decision drafts, even hygiene like merging duplicate claims.
- **Auto-apply, per playbook, opt-in:** unlocked by track record, offered by the product — "this playbook's suggestions were accepted 47 of 49 times; auto-apply internally and keep a change log?" Internal writes only; everything revertible.
- **Outbound — anything addressed to a human** (a Slack post, a Jira comment, an email): draft-and-approve, permanently. The user is always the sender. An agent crossing from tool to teammate uninvited is the single fastest way to get a PM's tool banned by their own stakeholders.

Trust is earned workflow by workflow, never granted globally — which mirrors exactly how a PM learns to delegate to a new chief of staff. One failure mode to design against explicitly: rubber-stamping, which quietly reintroduces the verification tax as reviewing debt. Countermeasures: per-playbook accept-rate and edit-distance analytics, and occasional spot-audit prompts ("you've batch-accepted 30 in a row — want a sampled deep-check of five?").

## 7 · Wedge and sequencing

Criteria for the wedge: daily-or-weekly frequency; genuinely hated toil; adoptable single-player without team buy-in; **builds the brain as a byproduct**; not already owned by a strong AI-native incumbent.

Scoring the candidates against that bar. *Feedback synthesis:* real pain, but Enterpret, Dovetail and Cycle are dug in, and for many PMs it is episodic rather than weekly — a fast follow, not the spearhead (though note the eventual advantage: in this graph, feedback lands next to decisions and the roadmap, which no point tool can offer). *PRD drafting:* commoditizing fast — ChatPRD and every doc editor's AI button — and it is the worst verification-tax surface to lead with; drafting alone doesn't build the brain. *Status and stakeholder updates, plus "what's the status of X and why":* weekly-to-daily frequency; universally resented; perfectly single-player; produces visible output that markets itself when a stakeholder asks "what made this?"; and — decisively — it is a *forcing function for the brain*, because to say what changed and why, the system must model state, deltas, and rationale.

**Recommendation: the wedge is Ask-with-receipts plus the Weekly Update playbook** — two faces of one engine, "model what changed and why." Everything else rides on the substrate that engine forces into existence.

Sequencing: **Phase 0**, connectors and the First Brief. **Phase 1**, the wedge, single-player. **Phase 2**, interview/feedback synthesis and live PRDs — where the brain's differentiation becomes visible against point tools. **Phase 3**, the shared brain: the decision log as org memory, alignment views, multiple PMs — where network effects and pricing expand. Stakeholders consume views free, in Slack and Confluence where they already live; seats are for brain owners. Every viewed update is an advertisement inside the buyer's own company.

Why incumbents don't simply do this: Atlassian Rovo is structurally Jira-gravity — its brain is tickets, and the seams between tools are precisely what it cannot see. Notion is doc-centric — artifacts without claims, text without truth-maintenance. Enterpret owns one signal type. The wedge lives *between* them, and a derived, read-only layer can sit on top of all of them without asking anyone to switch anything. The moat is the accumulated graph of confirmed claims and decision history: it compounds daily, it is private to the team, and it does not ship with an export.

## 8 · Non-goals for v1

Not a Jira or Linear replacement — tickets stay where engineering lives; the product reads them and drafts into them on approval. Not a doc editor competing with Notion — artifacts can sync and export outward; the win is truth-maintenance, not typography. Not autonomous outbound — no unsupervised messages to humans in v1, and probably ever. Not a general "AI workspace" — the PM-shaped object model *is* the product; chasing generality is how you lose to Notion on their terms. A useful internal test: if a feature neither reads from nor writes to the six objects, it doesn't ship.

---

## 9 · Riskiest assumptions, and the cheapest test for each

**1. Claim extraction is good enough that confirming beats writing.** If the First Brief is 60% noise, the entire posture collapses into a chore. This is testable *now, before any product exists*: run an extraction pipeline over your own discovery corpus — the interview transcripts and notes you already have — and measure the accept rate you yourself would give it. Highest-information experiment available, essentially free.

**2. PMs will actually review suggestions rather than rubber-stamp or ignore them.** Test in design partnerships with accept-rate and edit-distance telemetry from week one; treat a >95% blind batch-accept rate as a red flag, not a success metric.

**3. Update toil is a top-three unprompted pain, ahead of synthesis toil.** The Mom Test corpus you're building answers this directly: count unprompted mentions of status/update toil versus synthesis toil versus drafting toil before committing the wedge. If synthesis dominates, the wedge order flips — and notably, the architecture doesn't change. That resilience to wedge uncertainty is the practical payoff of the harness shape.

**4. Security review passes on read-only scopes.** Draft the scopes/DPA one-pager early and walk it past two friendly security teams before it's ever blocking a deal.

**5. The brain compounds fast enough to hold retention before the team phase.** Leading indicators to watch from the first design partner onward: confirmed claims per active week; share of asks answered from the brain versus fresh retrieval; artifact-health interactions per user.

---

*The compressed version of all of it: build the repo, not the autocomplete. Claims with receipts, decisions with history, artifacts that know when they're stale, an agent that can only say what it can cite, and a PM who is always the editor — never the audience.*

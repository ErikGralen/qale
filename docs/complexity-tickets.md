**Proposal:** Pick one noun — recommend **Chat** — and sweep all copy. Rename the agent-asks-you
card vocabulary to "Question" so "Ask" only ever points memory-ward.

**Decision:**
I want to use "Session" since it is MORE than chat. But yes we SHOULD sweep and unify. "Question" for the agents-asks-you sounds good.

**Implementation notes:**
Done 2026-07-30. Session is now the only noun the user reads: the sessions list
(header action, empty states, delete confirm), the session page (crumb, "New
session", mark done/reopen tooltips, empty hint, "Opening the session…", the
no-API-key line), the note's right panel ("Session", "New session about this
note", the session-files blurb), the tab-strip panel toggle, ⌘K ("New session"),
NoteView's receipt button ("Open the session"), and the agent runtime's user-
visible strings ("Session" / "Untitled session" fallback titles, "This session is
still responding", "…in Settings to start a session"). The Inbox's other sense of
the word went too: "Sent this session" → "Sent just now", "dismissed this
session" → "dismissed so far". Sidebar's Memory tooltip dropped `sessions` (no
longer a shelf, ticket 2) and its Sessions tooltip dropped "past conversations".
Renamed only what would re-seed the confusion: `ChatsView`→`SessionsView`,
`ChatView`→`SessionView` (+`ChatSession`→`SessionThread`, `onNewChat`→
`onNewSession`, `SideChat`→`SideSession`), `AskItem`→`QuestionItem`,
`AskCard`→`QuestionCard`, and `AttentionKind 'ask'`→`'question'` in
lib/attention.ts, which fixes the noun in the sidebar, Home, ⌘K and the Inbox at
once. Deliberately untouched: `chats:*` IPC channels, `ChatRefDTO`/`AskRequestDTO`
and the rest of the DTOs, `openChat`, the `session` note type, `sessions/` on

the agent's own system prompts in packages/agent (model-facing, not user-facing).
Question now names: the Inbox's lead section (was "Asked you"), the attention
item's meta and the sidebar's reason chip (both were "asked you"), the session
tool trail ("Raised a question", was "Asked you"), and QuestionItem/QuestionCard.
Ask stayed put and now only points memory-ward: the sidebar Ask row, the `ask`
skill, the send button, the docked composers, and the two card buttons that were

## 3. Single attention count

**What:** `attentionCount` (sidebar), `pendingCount` (Home/⌘K), and the Inbox's `needCount` are
three different arithmetics all presented as "what's waiting". The arrival vision names "two
inboxes" as a failure signal.

**Proposal:** Define one attention list in one place with one count; every other surface (Home
top-4, badge, Inbox) is an explicitly ranked view of that same list.

**Decision:**
Yes good!
**Implementation notes:**
The three arithmetics were: `attentionCount` = main's `pendingCount` + unread active
sessions (sidebar badge); `pendingCount` = raw pending cards, pushed from main on
`proposals:changed` (Home's card row, ⌘K's "N pending"); `needCount` = cards + unread
results recomputed from the renderer's own `proposals` array (Inbox header). They
disagreed on parked questions (counted nowhere, though a question is the one thing that
can never resolve itself), on shelved sessions (Home listed done/dismissed unread ones,
the badge did not), and on their source of truth (main's count vs the renderer's list,
which drift between the event and the refresh). Now: `lib/attention.ts` builds one ranked
list — ask → card → result → next meeting → unfiled review → due commitment → librarian
ping — each item `{id, kind, label, meta, tone, target, when?}`, built once in
app-state and exposed as `attention`. Named filters: sidebar badge, ⌘K and the Inbox
header all print `waitingCount` = `waitingOnYou(attention).length` (ask+card+result);
the Todos badge is `countOf(attention, 'todo')`; the Inbox's suggestion count is
`countOf(attention, 'ping')`; Home is `homeRows(attention, 4)`, which drops pings and
puts cards, reviews and commitments behind one door each. `pendingCount` is gone from the
renderer entirely (the IPC event still carries it; the handler now just refreshes).
Visibly changed: the badge and ⌘K now include parked questions, so the Inbox grew an
"Asked you" section at the top of its queue (answer-only, no dismiss) — otherwise the
badge would send the PO to a page that did not hold what it counted; ⌘K reads "N need
you" instead of "N pending"; Home no longer lists unread sessions the PO already shelved.
Main's dock badge still calls `ctx.proposals.pendingCount()` — it is a boolean in a
process that cannot see this list, and was left alone. Tests: `test/attention.test.ts`
(12 cases, incl. the ticket 11 cancelled-meeting guard).

## 4. Surface the layer as the mutability explanation

**What:** Why a note is editable / append-only / read-only / sync-owned looks like 13 arbitrary
per-type rules. The real rule is the layer (raw / derived / authored / sync-owned), which exists
in code but is never shown.

**Proposal:** One-line explanation on every read-only surface ("Mirrored from Jira — edits happen
there", "Raw material — never rewritten"). Present `ticket`/`wikipage` as **mirrors**, not memory
types.

**Decision:**
Yes good, but really think about how to present this in an intuitive way that is cleean. And dont use llm-isms like em dashes

**Implementation notes:**
Done. The single mapping is `packages/domain/src/notes/edit-layer.ts` (exported from `@qale/domain`), which *derives* one ownership layer per type from the rules that already exist (`TYPE_RULES` + `NOTE_TYPE_META`) instead of keeping a second list: `open` (body editable), `mirror` (type is bound to a provider enum), `spine` (`appendOnly`), `raw` (frozen body, raw layer), `receipt` (frozen body, derived layer). `readOnlyReason(type, frontmatter?)` returns the one sentence, null when the note takes a cursor.
The sentences: mirror = "Mirrored from Jira. Edits happen there." (source read from the note's own `provider`, so Linear/Notion need no new copy); raw = "Raw material. Never rewritten."; receipt = "A record of what happened. Kept exactly as it was filed."; spine = "Superseded, never edited. Write a new one to change course."
It renders as one quiet muted line with a small lock glyph directly above the read-only body in `NoteView.tsx` (the old bordered `bg-muted/40` callout is gone), plus a trailing "Open the original" link on mirrors since the URL row is a collapse away. Same sentence reused in the Memory shelf subtitles for the two mirror shelves.
`ticket`/`wikipage` now label as **"Jira mirror" / "Confluence mirror"** via `noteTypeLabel(type, frontmatter?)`, used by the NoteView type badge (the `capitalize` class is gone, labels are sentence case at source), `NoteList`, `QuickSwitcher` hits, and the ContextView section headings ("Jira mirrors"). FolderView empty states for both folders now open with "No mirrors yet."
Covered by `packages/domain/test/edit-layer.test.ts`, including an invariant test that a sentence exists for exactly the types `isBodyEditable` says are frozen, and a copy test (no em dashes, no semicolons, ≤70 chars). Ticket 8 is unblocked: this module is about editability only and says nothing about what a type *is*.

## 8. Per-type lifecycle names

**What:** `status` is polymorphic — `active` alone means three things (note, decision, customer).
Themes already broke ranks correctly with `stance`.

**Proposal:** Give each lifecycle its own name (decisions: *standing*, customers: *relationship*,
…) or at least never render two lifecycles under the same "Status" label.

**Decision:**
Yes i like this, i think each type of note should have different shapes. We should use hard coded enums for now. 

**Implementation notes:**

Built. `packages/domain/src/notes/lifecycle.ts` is the new table (field name + enum + human label per lifecycle); `frontmatter.ts` declares the keys, `edit-layer.ts` is untouched and still owns the ownership axis.

| type | field | values |
| --- | --- | --- |
| source, meeting, insight, note, ticket, wikipage | `processing` | new, processed, stale |
| decision | `standing` | active, superseded |
| customer | `relationship` | prospect, active, churned |
| todo | `commitment` | open, done, dropped |
| theme | `stance` | exploring, watching, committed, wont-do (unchanged) |
| person, session, skill | none | a type that never moves shouldn't look like it does |

Six types share `processing` because it is genuinely one lifecycle (has the workspace worked this material, and does that still hold), not six under one label. Its old fourth value `active` is gone: it only ever meant "done and relied upon", which is `processed`.

Old `status:` on disk: `normalizeLifecycleKeys` folds it onto the type's own key on every read (`parseFrontmatter`) and every write (`FsVault.writeNote`), mapping `active` → `processed`, so vaults migrate as notes are saved and nothing is destroyed. It only renames a value the lifecycle recognises, so a foreign `status: draft` survives as the unknown key it was. vault-dev fixtures moved to the new keys.

Left alone on purpose: meeting `event_status` (Google's word for its own event, including `cancelled`), ticket `state` / `state_category` (the tracker's workflow), wikipage `version`, and the proposal/ping `status` columns in the app DB. None are lifecycles the PM moves a note through. The skill `kind` lattice is untouched per the skills-enum ticket, including its display labels.

Renders: no surface labels two lifecycles "Status" any more (properties rows, folder facet chips, NoteView badges, index.md section headings all read the lifecycle's own name and the value's label, so `wont-do` shows as "Won't do" and `in_progress` as "In progress"). The index carrier is now `lifecycle` (SQLite column, `IndexedNote`, `NoteRefDTO`), SCHEMA_VERSION bumped to 3 so the derived DB rebuilds.

Open: the IPC verb `todos:setStatus` and the use-case `setTodoStatus` keep their names (renaming them means editing `handlers.ts`/`packages/ipc`, owned in parallel), as does `renderer/src/lib/note-status.ts`.

## 12. Teach the mention→mirror rule once

**What:** Writing `[[INFRA-88]]` silently starts mirroring it plus up to 100 blockers into
`tickets/`; cap overflow is a console.warn. Because every instance is silent, the user can never
learn the rule.

**Proposal:** One quiet housekeeping line on first track ("Now following INFRA-88 — you mentioned
it in Pricing v2"). Make cap truncation visible.

**Decision:**
When do we trigger this? we should perhaps prompt the user in a super clean way. 
**Implementation notes:**

**What actually fires, and when.** Nothing happens when you type. `syncTracked`
(`apps/desktop/src/main/services/sync-service.ts:645`) runs on the 5-minute maintenance tick
(`runMaintenance`, `apps/desktop/src/main/handlers.ts:172`), rescans the whole index through
`deepTargets` (line 588) and calls `store.track('atlassian', 'ticket', key, 'link', now)` for every
ticket key any non-mirror note links. That call is an upsert, so it cannot tell the first track from
the five-hundredth. Both missing facts are one line away: `store.trackedSource('atlassian', key)` is
`null` before the first track, and `deepTargets` already walks the notes, so returning
`Map<key, notePath>` instead of a `Set` gives you the note it was mentioned in. Blockers arrive later
in the same tick: `trackBlockers` (line 695) runs from inside `writeMirror`, so the blocker count for
a key is only known at the end of the tick, and the cap check (line 707) `console.warn`s and returns.

**When to trigger: after the fact, once, batched at the end of the tick that first mirrored it.** Not
a confirmation at mention time, for three reasons. There is no mention-time moment in this code (the
track is up to 5 minutes after the keystroke, and the same key can arrive by paste or by an agent
writing the note). Tracking is a read, and this file's own hard rule (line 43) is that reads take no
card and no dialog. And the end of the tick is the only point where "and 7 tickets blocking it came
along" is known. 2nd, 10th and 100th mention: silent, no exceptions. The teaching moment is the first
`link`-sourced track in this workspace ever, flagged once (a `qale.sync.taughtFollowing` style flag);
after that the rule is learned and the rail stays quiet.

**What it says.** An after-the-fact quiet line with an undo, not a question. Reuse the receipt rail:
the same card shape as `ArrivalReceipt.tsx` portalled into `RAIL_SLOT_ID` (`toast.tsx`), no timeout,
"Stop following" sitting where "Undo all" sits (`untrackExternal` already exists at
`sync-service.ts:733` and has no renderer caller yet). Push it on the existing `connections:changed`
event (`handlers.ts:157`). Copy, first time only:

> Now following INFRA-88, you linked it in Pricing v2. Linked tickets stay in sync here.
> [Stop following]

and when that first track dragged dependencies in, one clause more: `Now following INFRA-88 and the
7 tickets blocking it.`

**Cap truncation.** The cap is not a moment, it is a state that persists until someone untracks
something, so it does not belong in the rail. Put it as an inline maintenance row on the Atlassian
connection card in Settings, the same shape as `TokenRenewal` (`ConnectionsSettings.tsx:253`), driven
by `countTrackedBySource('atlassian', 'blocker') >= BLOCKER_TRACK_CAP` on the connection DTO: "Following
100 blocker tickets, the most it will follow. New blockers are not being added. Stop following some to
make room." That row is also the standing answer to "what am I following?", which is what makes it safe
to go quiet after the first line.

**Cost and cut line.** Half a day: `deepTargets` returns a Map, one `trackedSource` pre-check, one
field on the changed event, one small rail card, one taught-once flag, one connection row. Risk is
low; the copy is the only part worth arguing about. If it feels heavy, drop the note attribution
("you linked it in Pricing v2") and ship the bare line, and drop the blocker clause. Do not cut the
cap row: silently following 99 of 140 blockers is the one part that is a correctness bug rather than
a teaching problem.

**Recommendation:** one quiet rail line on the very first link-track ever, silent forever after, plus
a permanent cap row on the Atlassian connection card. No confirmation dialog anywhere.

## 13. Fix: discarding all cards marks the meeting reviewed

**What:** Resolving the *last* card of a session flips the meeting to `processed` on accept
**and reject** — discard-all currently means "reviewed". Wrong statement about the user's
attention; treat as a bug.

**Proposal:** Only flip on at least one accept, or keep the meeting in "needs review" when
everything was discarded.

**Decision:** I think we should prompt the user with a nudge perhaps, set status to processed? super clean nudge that is quick.

**Implementation notes:**
Confirmed: `completeMeetingReview` (`packages/application/src/use-cases/proposals.ts`) flipped the meeting to
`processed` whenever the last card of a session resolved, accept or reject alike. New rule: it flips silently
only when at least one of the session's cards ended `accepted`; when every card was rejected (or went stale) it
writes nothing and returns `{ ask: { path, title } }` instead. Cancelled and already-processed meetings are
never asked about, so the `needsReview` cancelled rule is not regressed. The write itself moved into a new
`markMeetingReviewed(ctx, path)`, shared by the silent close and the new `meeting:markReviewed` IPC.
The ask rides back on the `proposals:accept` / `proposals:reject` result and the Inbox renders it as one quiet
strip where the cards just were: "Nothing kept from *Roadmap sync*. Mark it reviewed?" with a **Mark reviewed**
button and a **Not yet** dismiss. "Not yet" leaves the meeting in needs review and is remembered per workspace
in `localStorage` under `qale.reviewAskDismissed.v1:<vaultPath>` (view-only state, like the pin set), so the same
meeting is never asked about twice. Covered by `packages/application/test/complete-meeting-review.test.ts`.

## 15. Report `extras` sessions in the arrival receipt

**What:** Extra bound skills fired on capture run headlessly and never appear in the receipt —
it says "2 reviews started" while a third runs unreported. Violates "the receipt is the
interface".

**Proposal:** Count and link every fired session in the receipt, extras included.

**Decision:**
Not sure what you mean by this, what do you mean? examples

**Implementation notes:**

**What `extras` are.** When material lands, `boundFollowUps`
(`packages/application/src/use-cases/notes.ts:307`) asks `skillsForEvent` which skills bind to
`capture.transcript` / `capture.ingested`. The FIRST hit becomes `followUp` (the session you get
opened into); every further hit becomes `extras`, marked `background: true`. Both capture entry points
fire and forget them: `handlers.ts:659` (`capture:ingest`) and `handlers.ts:842` (`arrival:ingest`)
both do `for (const extra of item.extras ?? []) void fireSession(...)` and throw the handle away. The
receipt's number is `reviews: out.filter((i) => i.session).length` (`handlers.ts:874`), and only
`followUp` ever sets `session`. So an extra is uncounted, unlinked, and its failure does not raise
`reviewsFailed`. The pre-flight tray under-reports the same way: `resolveRuns`
(`use-cases/arrival.ts:272`) takes `hits[0]` and discards the rest.

**Is it real today? Real in the code, not reachable with the skills we ship.** Only
`skills/arrival.md` binds capture events, in `vault-dev/` and in `packages/sessions/src/defaults.ts`,
and its four bindings are mutually exclusive on `when` (`origin: po|external`, `kind: link|screenshot`),
so exactly one hit fires per item and `extras` is always empty. `vault-dev/skills/broken-demo.md`
looks like a second `capture.transcript` binding but its `mode: whenever` is invalid, so `parseSkill`
drops it, which is the whole point of that file. So the audit's "a third runs unreported" is not
something you can see today. It goes live the moment anyone adds a second capture-bound skill, which
the Skills view actively invites.

**Constructed example** (constructed, not observed). Add to `vault-dev/skills/commitment-check.md` a
binding `mode: triggered, event: capture.transcript, when: {origin: po}`, then drop
`demo-samples/nordkap-post-sso-checkin-transcript.txt` into the app. Two sessions start: "Handle new
material" (`arrival`) as the foreground one, and the commitment check headlessly. The receipt says
"1 review started" and lands you in the arrival session. The commitment check runs invisibly; its
cards turn up in the Inbox minutes later with no explanation of where they came from, and if it dies
you get an OS notification (`handlers.ts:307`) while the receipt still reads as if all was well.

**If fixed:** the receipt says "2 reviews started", and the "N reviews in Sessions" line
(`ArrivalReceipt.tsx:111`) counts them too. That means keeping the handle `fireSession` already
returns for extras and carrying it into the outcome item, plus counting extras in `reviewsFailed`.
Small change; worth doing before the first user binds a second capture skill, not after.

Status: IM-1..7 and IM-9..15 BUILT 2026-09-05 by seven subagents (IM-8 skipped, IM-10 the cheap
version). Typecheck and tests green in every package (domain 251, application 227, agent 325,
vault 49, sessions 51, desktop 398). The maps were rendered from a copy of the demo vault

How the agent finds files. Split out of the 2026-09-05 question: now that Documents has
folders, how do the index files keep up, and what do we do about meetings and todos, where
time matters more than a name.

The facts here come from one read of the code on 2026-09-05 (working tree, uncommitted). The
starting point is better than the question assumed:

- Index files exist and are generated by code, not by a model. `generateIndexFiles` in
  `packages/application/src/use-cases/index-files.ts` runs on every 5-minute librarian tick.
  It writes a root `index.md` plus one per type folder, grouped by lifecycle, and only rewrites
  a map whose content changed. One commit per pass.
- They are already invisible. Every list, the search, and the agent's list tool filter
  `index.md` out. The root map is seeded into every session's context.
- Each line in a map is the note's `summary` field. The map is only as good as the summaries.

So there is no new system to build. There are three gaps, and a model belongs in exactly one of
them.

Write your call under **Decision** ("build", "skip", "discuss…"). **Notes** is for anything
the build needs to know. Nothing gets built until its Decision field is filled in.

Order: A first (small, pure, fixes a visible defect). B and C are independent of each other and
of A. D, E and F are independent of everything, except that IM-13 needs IM-11 and IM-15's
sort rides on IM-3.

## A. Time-shaped folders

The meetings map sorts by title and drops the date. Today it shows "Nordkap Checkin" twice
with nothing to tell them apart. The todos map groups by commitment but sorts open todos by
title, so the one due tomorrow sits wherever its title lands.

### IM-1. Meetings map: by month, newest first, date on every line

**What:** `renderFolderIndex` is one renderer for every type. It knows lifecycle, and nothing
else about the notes it lists.

**Change:** Let the renderer know the type. For meetings, group by month (`## 2026-07`),
newest month first, newest meeting first inside a month. Each line starts with the date, then
the title, then the summary, then the customer link when there is one:

```
* 2026-07-14 [Nordkap check-in](meetings/2026-07-14-nordkap-checkin.md) — SSO date confirmed… ([[customers/nordkap-payments]])
```

Meetings with no date (there should be none, but the schema allows it) go under "Undated" at
the end. `IndexEntry` grows `date` and `customer`; `collectFolders` fills them from the index.

Review 2026-09-05: `IndexedNote` has no `date` or `customer` field, only `frontmatter`;
`dto.ts` already extracts `date`, `due` and `owner` and is the pattern to copy. `customer` is
a wikilink string, so the line resolves it through `index.resolve` and prints the title with
a path link, not a `[[...]]` (the maps are markdown-path links throughout). The sample line
above is wrong on that point.

**Not in scope:** relative buckets ("This week", "Upcoming"). They change at midnight, which
means a rewrite and a commit every day. The session already gets today's date at start, and it
can read a month heading. Time-relative views belong in the tool (IM-3), not in the file.

**Decision:**
yes
**Notes:**
Built. `renderFolderIndex` branches on `typeForDir`. Customer resolved in the application layer to a title with a path link; unresolved prints the bare target. Series slug appended (IM-10). Domain 239→250 tests.

### IM-2. Todos map: open ones by due date, owner on the line

**What:** Open todos sort by title. The line does not show who owes it or when.

**Change:** Keep the commitment groups (Open, Done, Dropped). Inside Open, sort by `due`
ascending, undated last. Each line carries the due date and the owner:

```
* due 2026-07-16 · Sara Lindqvist — [Send Nordkap's security-review scope](todos/…) — …
```

Done and Dropped keep their title order; nobody scans those for time.

Review 2026-09-05: `owner` is a wikilink (`[[people/sara-lindqvist]]`), so the name comes
from resolving it to the person note's title. `due` is only shape-checked at write time; an
old note can carry `due: next Friday`, which must sort as undated, not after every real date.

**Decision:**
yes
**Notes:**
Built. Open sorted by `due`, undated last; owner resolved from the wikilink; `dayOf()` accepts only YYYY-MM-DD.

### IM-3. Time filters on the list tool

**What:** `vault_list` filters by type and lifecycle only. A question like "what did we
discuss with Nordkap in June" has no tool that answers it. The agent reads the whole meetings
map, or greps.

**Change:** Add `since`, `until` and `sort` (`date` | `title`) to `vault_list`. The date is the
type's own day field: `date` for meetings, `due` for todos, `mtime` for the rest. Update the tool
description so the agent knows the map is orientation and the tool is where time questions go.

**Review 2026-09-05:** day fields on old notes are unchecked strings. `since`, `until` and
`sort: date` treat anything that is not `YYYY-MM-DD` as undated.

**Why this and not folders:** Splitting meetings into `meetings/2026/07/` was considered and
rejected. Everywhere outside Documents the folder is the type (`moveNote` refuses to move
anything else for this reason). Year folders would break the sync engine's write paths and the
"filename carries the date" convention, for a grouping the renderer can give us for free.

**Decision:**
yes
**Notes:**
Built on `vault_list`: `since`, `until` (inclusive), `sort` (date | title | modified). Day is `date` for meeting/decision, `due` for todo, mtime day otherwise; malformed days are undated. Rows now show the day. Shared `listRow` with `vault_backlinks`.

### IM-4. Cap the meetings map

**What:** A folder map is one on-demand read. Today's meetings map is about 2 KB. A year of
meetings at three a day is 700 lines, about 77 KB, roughly 20k tokens per read. (The 19 KB
figure quoted earlier was all 16 maps together; only the 1.8 KB root map is seeded into the
session.) At that size the map stops being orientation.

**Change:** Snap the window to whole months. The map lists this month and the two before it
in full, plus everything upcoming. Older months collapse to one line each: `## 2026-03 (14
meetings, use vault_list since/until)`. The file then changes when a note changes and once at
the turn of the month. No daily commits. Needs IM-3, or the agent has no way to reach the
collapsed months.

**The dynamic question, settled:** files stay files, and the seed is the dynamic view.
Everything relative to today (this week's meetings, todos due soon, IM-15's "what moved") goes
in the session seed, which is already generated text with the date in it. The maps on disk
never carry a relative bucket. Reasons, from the brainstorm and the review:

- The in-app agent reads through `vault_read` either way, so a virtual map would not read
  differently to it. But anything outside the app reads the folder as files, a person
  debugging opens the map to see what the agent saw, and "the workspace is a folder of
  markdown with the maps in it" is one rule instead of two.
- Documents folders exist because `notes/<folder>/index.md` exists (`lib/documents.ts`,
  `createDocumentFolder`, `deleteDocumentFolder`, `renameDocumentFolder`). 21 test files
  reference `index.md`.
- The seed is baked into the system prompt at session start, not per turn. A "live" seed is
  as live as session start, the same as the date preamble. That is fine for a seed and would
  have been a false promise for a "live" map.
- Not a cost after all: there is no OKF exporter in the code, Obsidian appears only in
  comments, and the MCP server searches the index and never reads `index.md`. The disk file
  is for people and for outside tools that read folders, not for any code we ship today.

**Decision:**
would it be possible to make this dynamic instead? so we dont have to keep a file udpated. Please brainstorm this with me.
→ yes, build it as written above (files static, seed dynamic, month-snapped window). 2026-09-05.
**Notes:**
Built. `renderFolderIndex(folder, { today })`: this month and the two before in full plus upcoming, older months collapse to `## YYYY-MM (N meetings, use vault_list since/until)`. Only the month of `ctx.clock.now()` is used, so the file is stable within a month. First tick after this lands rewrites every map once.
Brainstorm 2026-09-05. The renderer can run at read time instead of on the tick: the seed
and every folder map rendered from the index when asked for, with today's date. Three cuts:

1. **Virtual only.** No `index.md` on disk. The seed and every folder map are rendered on
   demand (a read of `meetings/index.md` returns the live rendering). No commits, no churn,
   relative buckets ("This week", "Upcoming", "Last 90 days", older months collapsed) come
   free. Costs: the OKF export, the map a person sees in Obsidian or Finder, and the
   Documents folder marker (`notes/<folder>/index.md` is what makes an empty folder exist).
2. **File only** (today). Stable and shareable; can never know what day it is.
3. **Both from one renderer.** The agent reads the live rendering; the disk file is the
   time-free export, regenerated only when a note changes.

Erik wants to brainstorm 1 vs 2 further. Open questions: are the disk files wanted at all
(OKF export, opening the folder outside Qale)? Should the dynamic seed carry a time-relative
slice (this week's meetings, todos due within 7 days), or stay a pure map with time left to
IM-3's tool?

## B. Documents subfolders

### IM-5. Map the Documents tree

**What:** A Documents folder's `index.md` is a stub written once by `createDocumentFolder`
("Specs, a folder of your documents") and never touched again. `collectFolders` groups by
type, so every document at every depth lands in the flat `notes/index.md`. The subfolder maps
say nothing, and the top map ignores the structure the PM built.

**Change:** Make the generator descend, inside `notes/` only. `notes/index.md` lists
subfolders first (name, one-line purpose, recursive count, link to the subfolder's map), then
the documents at the root level. Each `notes/<folder>/index.md` is generated the same way,
one level down. Folder deletion already removes the file; folder rename already moves it.

The generator keeps the `description` line from the existing file when it has one. That is
where a folder's purpose lives, and it must survive regeneration so IM-7 has somewhere to
write. The stub helper stays as the seed for a new folder.

**Decision:**
yes
**Notes:**
Built. `collectFolders` is async and descends under `notes/`: subfolders first (purpose, recursive count), then documents; each `notes/**/index.md` generated one level down. Purpose read back from the file's `description` (and `purpose_of`, IM-7), else `documentFolderPurpose(title)`, which `folderIndexStub` now shares.

## C. Where a cheap model earns its place

### IM-6. Summaries for typed documents, written silently

**What:** A document made in Qale gets `summary: <title>` (`createNote`) or the first line
of the body (`captureNote`). Neither sets `needs_summary`; that flag marks files that
arrived with no summary at all (drops, external edits), and normalize deletes it again as
soon as the summary differs from the body's derived first line. So the Documents map is a
list of titles and first lines, and the only fix today is an agent happening to open the
note and proposing an update the PM then approves.

**Change:** A summariser pass on the librarian tick. It picks notes whose summary is still
the placeholder (equal to the title, or to the body's derived first line) or whose body
changed since the summary was written. It asks a cheap model for one line grounded in the
body, writes `summary`, deletes the `needs_summary` key if present, and commits once per
pass ("librarian: summaries").

Rules:

- **This is a machinery writer outside the write policy, and the ticket says so.** The
  policy returns `ask` for any write under `notes/` unless the PM asked in chat, and it is
  only consulted by proposals. The tick's normalize pass already writes frontmatter outside
  it, justified as "machinery, not authorship". A summary is the same kind of thing: a
  retrieval label for the PM's own text, reversible through history, never a claim. If that
  argument does not hold for model output, the fallback is one grouped card per pass.
- **Selection by marker, not by author.** No field records who wrote a note, and the commit
  prefixes (`note:`, `update:`) cover both approved cards and silent asked writes. So the
  rule is: summarise when the summary is a placeholder or the body changed since
  `summary_at`. Mirrors are excluded by type. A note an agent wrote has a real summary and
  never matches.
- **The marker is `summary_at`** (ISO date of the summary write) with a short body hash
  beside it, so "changed since" is one comparison. Unknown keys survive every write, but both
  keys must be added to the hidden-field lists in `properties-schema.ts` and `reference.ts`.
- **Delete the flag, don't set it false.** Normalize deletes the key; a `false` would be
  rewritten and committed again on the next tick. The prompt paragraph in `prompts.ts` that
  says "set needs_summary to false" changes to match.
- **The model entry point has to be opened up.** The cheap-model picker is behind a private
  method on the runtime (`completeCheaply`). Expose a `summarise(system, prompt)` on it and
  gate the pass on an active key, the way the tick already gates the librarian.
- **Collisions are benign.** A session's `propose_update` on the same note merges
  frontmatter at accept and its summary wins; a summary write between draft and approval
  does not fail the card. Each write fires the watcher (reindex, one repaint) and no loop.
- Batches are small (say 20 per tick). One sentence, plain words, in the note's own language.

**Why the model writes the line and not the map:** the map stays a pure function of the
summaries, so it is always consistent and never needs review. Model output is confined to one
line per file, the one thing code cannot do.

**Decision:**
yes
**Notes:**
Built: `packages/application/src/use-cases/summaries.ts` (`planSummaries`, `applySummaries`, `runSummaryPass`), prompt in `packages/agent/src/summaries.ts`, public `AgentRuntime.summarise`. Runs on the tick after normalize and the librarian, before the maps, gated on an active key. Markers `summary_at` + `summary_of` (djb2 body hash), hidden in reference.ts and properties-schema.ts. `needs_summary` is deleted by the pass; the prompts.ts paragraph tells the agent to leave the key out of a proposal (an accept-time merge cannot delete a key). No live model run.

their meetings through the edge index, and the UI shows them as grouped backlinks. Two things
are missing on the agent's side.

## E. Tags as the third axis

Folder is the type, links are the relation, tags are the project or area. The UI already
treats tags that way: the tag page groups everything tagged, across every type, in spine
order. The agent side is missing. Every proposal tool tells the agent to add 1 to 2 tags
"drawn from tags already in use", but no tool lists the tags in use, no tool filters on them,
and the tag page's Ask sends one sentence ("Scoped to notes tagged pricing") that the agent
has no way to act on. The index carries every note's tags in its frontmatter, so nothing
below needs a schema change.

Not proposed here: more tags, or a model that adds them. A tag is a judgment about what
belongs together, and a background pass would drift the vocabulary. The 1 to 2 rule stays.

## F. What is moving

### IM-15. Recently worked-on notes, seeded into the session

**What:** The agent has no recency signal. The index stores each note's mtime, but
`vault_list` neither shows nor sorts by it, and the maps sort by title. "What is the PM
working on this week" is invisible to every session.

**Change:** Two parts.

1. A block under the vault map in the session context: the ten notes with the most real
   edits in the last seven days, one line each: path, summary, edit count, who (you, Qale,
   or both). Labelled as a hint ("what moved this week"), not as the way in.
2. `sort: recent` on `vault_list`, as part of IM-3's `sort` parameter, for when the seed is
   not enough.

**Source:** git, not mtime. mtime says when a file was last touched; one write and fifty
look the same. Every write is already a path-scoped commit with a message prefix, so one
`git log --since=7.days --name-only --format=%s` call gives the whole week in one go. Add
`changedSince(days)` to `GitPort` next to `history`.

**What counts as an edit:** the PM's own saves and applied proposals. Skip commits from the
sync engine and from the librarian (maps, and summaries once IM-6 lands). The prefix on the
commit message is the filter, as an explicit exclude list.

Review 2026-09-05, two corrections:

- **Count days touched, not commits.** The editor autosaves 1.5 s after typing stops and
  every save is an `edit:` commit, so ten minutes of writing is dozens of commits. Rank by
  distinct days (or hours) a path was touched in the window.
- **"Who" cannot come from the git author**; every commit has one identity. It comes from
  the prefix, and `note:`/`update:` cover both approved cards and silent asked writes, so the
  labels are "you" (`edit:`, `properties:`, `create:`, `capture:`, `rename:`, `move:`) and
  "approved or asked" (`note:`, `update:`, `decision:`, `todo:`, `processing:`, `pushed:`),
  never "Qale".

Prefix table as of 2026-09-05. Excluded: `sync:`, `librarian:`, `workspace: normalize`,
`session:`, `skills:`, `voices:`, `qale:`, `create folder:`, `rename folder:`,
`delete folder:`. Calendar sync skips unchanged events, so meetings are not rewritten on
every pull, but the exclusion still holds.

**Not in the maps.** Recency changes daily and the maps are committed files.

**Caution:** recent is not relevant. An agent that leans on this will over-weight whatever
the PM touched yesterday. Ten lines, seven days, and the label keeps it in its place.

**Decision:**
yes
**Notes:**
Built: `GitPort.changedSince(days)` (one `git log --since --name-only` call, NUL-marked headers), `## What moved this week` seed block (`whatMoved` in runtime.ts): ten notes by distinct days touched, who = "you" / "approved or asked" / "you and Qale" from the commit prefix. Prefix tables: you = edit, properties, create, capture, rename, move, source, transcript, verified, undo; approved or asked = note, update, decision, todo, processing, pushed, refile, delete; excluded = sync, librarian, workspace, session, skills, voices, qale, create/rename/delete folder.

## Not proposed

- **Splitting meetings or todos into date folders.** See IM-3.
- **A model writing the index files themselves.** The maps are a pure function of the
  frontmatter. Anything a model added there would drift from the notes within a tick.
- **A cheap-model tagging pass.** See section E.
- **Showing the maps to the PM.** They are for the agent. The Documents page has folders,
  Memory has shelves, and both read the same index the maps are built from.
- **Relative buckets in the file.** "This week" belongs in the session's date preamble and in
  IM-3, not in a file that would then change every night.
